Build a small Lex package named "webhooks": a signed-webhook inbox REST API that is safe to put on the internet. Reuse the existing packages lex-web (routing and serving), lex-schema (request validation) and lex-orm (database access, SQLite) instead of writing those layers yourself. Use the standard library's crypto module for HMAC-SHA256, hex encoding and constant-time comparison.

Configuration comes from environment variables. WEBHOOKS_SECRETS is formatted "source1:secret1,source2:secret2" (a source name is 1 to 32 characters of lowercase letters, digits, "_" or "-"; a secret is any text without "," or ":"). WEBHOOKS_ADMIN_TOKEN is the bearer token for reading events. The server listens on the port in WEBHOOKS_PORT, on the host in WEBHOOKS_HOST (default 127.0.0.1), and the SQLite database path comes from WEBHOOKS_DB.

Endpoints, all returning JSON:

- POST /hooks/{source} -- a sender delivers one event. Required headers: "X-Timestamp" (integer Unix seconds), "X-Event-Id" (1 to 64 characters of letters, digits, "_" or "-") and "X-Signature" of the form "sha256=" followed by 64 lowercase hex characters. The signature is the HMAC-SHA256, keyed with the source's secret, of the text <X-Timestamp> + "." + <raw request body>. The body must be a JSON object. On success: 202 with {"id": <integer>, "duplicate": false}, and the event (source, event id, receive time, body) is stored. If the same source has already stored the same X-Event-Id, nothing is stored again and the answer is 200 with {"id": <the original id>, "duplicate": true}. The same event id from different sources is independent.
- GET /events?source=NAME&limit=N -- requires "Authorization: Bearer <WEBHOOKS_ADMIN_TOKEN>". Returns {"events": [...]} ordered by id ascending, each event with "id", "source", "event_id", "received_at" and "body" (the JSON object that was sent). "source" is optional and, if given, must be a configured source (otherwise 400). "limit" is optional, an integer from 1 to 100, default 50 (otherwise 400).

Security requirements. Each one is something an attacker will try, and each must have a test:

1. A missing, malformed or wrong X-Signature is 401 and nothing is stored. The signature is checked against the raw bytes of the body exactly as received, before the body is parsed. A valid signature for one source must not be accepted for another source (different secrets).
2. An unknown source and a bad signature give the IDENTICAL 401 response (same status and body), so an attacker cannot learn which sources exist.
3. The signature is compared in constant time (no early exit on the first differing character), and secrets and the admin token are never logged or echoed in any response.
4. Replay protection: X-Timestamp must be within 300 seconds of the server's current time, past or future; otherwise 400 and nothing is stored. A missing or non-integer X-Timestamp, or an invalid or missing X-Event-Id, is 400 (checked after the signature, so an unsigned request is always 401).
5. A request body larger than 65536 bytes is rejected with 413 before it is read into the signature check or parsed. A body that is not a JSON object (an array, a string, invalid JSON) is 400, after the signature has been verified.
6. GET /events without the admin token, with a wrong token or with a malformed Authorization header is 401 and the database is not read; the token is compared in constant time. Every database query is parameterized: a "source" value such as `a' OR '1'='1` is simply not a configured source (400).
7. The server listens on loopback (127.0.0.1) by default; the host can be overridden by WEBHOOKS_HOST.

Effects. The pure logic -- parsing WEBHOOKS_SECRETS, building the signed text, checking that a timestamp is inside the window, validating an event id, parsing the pagination parameters -- must be pure functions with no effect annotation, each with examples. Only the handlers and main may use effects, and only the narrowest ones Lex allows (the database, the network, reading its configuration from the environment, the clock for the replay window, and crypto for the HMAC). Opening the SQLite database declares fs_write in the standard library, so the grants are net, sql, env, fs_write, crypto and time and nothing else; the server must never need process or general IO access.
